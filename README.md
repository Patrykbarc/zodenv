# zodenv

Generate type-safe, [Zod](https://zod.dev)-validated TypeScript schemas from your `.env` file. One command — autocomplete, runtime validation, and a `.env.template` kept automatically in sync.

## Install

```bash
npm install --save-dev zodenv zod
# or
pnpm add -D zodenv zod
# or
yarn add -D zodenv zod
```

`zod` is a peer dependency (≥ 3.22).

## Quick start

Given a `.env` like this:

```ini
API_URL=https://api.example.com
DB_PORT=5432
DEBUG=false
# @default production
NODE_ENV=
```

Run:

```bash
npx zodenv
```

You get `src/constants/env.generated.ts`:

```typescript
// Auto-generated by zodenv — DO NOT EDIT
import { z } from "zod";

export const ENV_NAMES = ["API_URL", "DB_PORT", "DEBUG", "NODE_ENV"] as const;

export const envSchema = z.object({
	API_URL: z.string().min(1),
	DB_PORT: z.coerce.number(),
	DEBUG: z.enum(["true", "false"]).transform((v) => v === "true"),
	NODE_ENV: z.string().default("production"),
});

export type EnvironmentVariables = z.infer<typeof envSchema>;

export const getEnvs = (): EnvironmentVariables => {
	const raw = Object.fromEntries(ENV_NAMES.map((name) => [name, process.env[name]]));
	return envSchema.parse(raw);
};
```

…and a `.env.template` next to your `.env`, ready to commit.

## CLI options

| Flag                 | Default                | Description                                                                   |
| -------------------- | ---------------------- | ----------------------------------------------------------------------------- |
| `--out-dir <dir>`    | `src/constants`        | Output directory (relative to the `.env` file, or absolute)                   |
| `--out-file <file>`  | `env.generated.ts`     | Output filename                                                               |
| `--env-source <s>`   | `auto`                 | `auto` \| `process.env` \| `import.meta.env`                                  |
| `--type-name <name>` | `EnvironmentVariables` | Exported TypeScript type name                                                 |
| `--env-file <path>`  | `./.env`               | Path to the `.env` file                                                       |
| `-r`, `--recursive`  | `false`                | Walk the current directory tree and process every package's `.env` (monorepo) |
| `-h`, `--help`       | —                      | Show usage                                                                    |
| `-v`, `--version`    | —                      | Show installed version                                                        |

### `--env-source auto`

`auto` (the default) detects the runtime by reading the neighboring `package.json`:

- depends on `astro`, `vite`, or any `@vitejs/*` → `import.meta.env`
- otherwise → `process.env`

Override explicitly with `--env-source process.env` or `--env-source import.meta.env`.

## Annotations

Comments directly above a variable override the inferred type:

```ini
# @type number
SOME_STRING_THAT_IS_ACTUALLY_A_PORT=8080

# @optional
FEATURE_FLAG=

# @default production
NODE_ENV=
```

| Annotation                        | Effect                        |
| --------------------------------- | ----------------------------- |
| `# @type number\|boolean\|string` | Override the inferred type    |
| `# @optional`                     | Mark as optional              |
| `# @default <value>`              | Set default, implies optional |

Annotations are cleared by blank lines — they apply only to the immediately following variable.

**Type inference defaults:**

| Value            | Inferred type      |
| ---------------- | ------------------ |
| `true` / `false` | `boolean`          |
| `3000`, `0.5`    | `number`           |
| anything else    | `string`           |
| _(empty)_        | `string`, optional |

## Runtime usage

### Option A — use the generated `getEnvs`

The generated file already exports `getEnvs`:

```typescript
import { getEnvs } from "./constants/env.generated";

const env = getEnvs();
console.log(env.DB_PORT); // number
```

### Option B — `createGetEnvs` factory

When you don't want the generated file to import from this package at runtime, use the factory:

```typescript
import { createGetEnvs } from "zodenv";
import { envSchema } from "./constants/env.generated";

export const getEnvs = createGetEnvs(envSchema, import.meta.env);
```

`createGetEnvs` parses and validates on the first call, then returns the cached result.

## `.env.template` sync

Every run automatically syncs `.env.template` next to your `.env`:

- New variables are appended with an empty value
- Variables removed from `.env` are removed from the template

Commit `.env.template` to version control so teammates know which variables are required.

## Monorepo mode (`--recursive`)

For monorepos, run from the repository root:

```bash
npx zodenv --recursive
```

The CLI walks the current directory, finds every `.env` whose folder contains a `src/` directory, and for each one:

- writes `<out-dir>/<out-file>` next to the `.env`
- syncs `.env.template` next to the `.env`

Ignored: `node_modules`, `dist`, `build`, `.git`, `.next`, `.turbo`, `coverage`, and any directory whose name starts with `.`.

## Programmatic API

`zodenv` also exports the building blocks if you want to script your own pipeline:

```typescript
import { EnvParser, CodeGenerator, TemplateSync, createGetEnvs } from "zodenv";
```

- `EnvParser` — parses `.env` content into typed entries.
- `CodeGenerator` — turns entries into the generated TypeScript source.
- `TemplateSync` — keeps `.env.template` in sync with the parsed entries.
- `createGetEnvs` — runtime factory that parses, validates and caches.
